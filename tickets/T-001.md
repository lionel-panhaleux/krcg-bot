## Problem

Deploy is undocumented outside README "Hosting the bot": a hand-made venv plus a
hand-written systemd unit with `DISCORD_TOKEN` inline. Nothing in the repo
automates or records it; the live instance's state exists only on the host.

`lionel-panhaleux/krcg-bot: gravelines` is already in server-setup's
`deploy-targets.yml`, so `just sync`/`sync-key` have pushed a live credential to
a repo with no consumer. Verified on the `production` environment:
`DEPLOY_SSH_KEY` (rotated 2026-07-04), `DEPLOY_HOST=152.228.170.51`,
`DEPLOY_HOST_KEY`. The only workflow on `origin/master` is `static.yml`.

## Outcome

A deploy pipeline living in this repo, runnable both from Lionel's laptop and
from CI, that installs a built wheel onto gravelines and restarts the unit. The
orphan credential gains its consumer.

## Advisor input

eng:
- server-setup ships only `nginx_site` and `postgres_db`. krcg-bot is a gateway
  client — no listener, no database — so neither role applies. There is nothing
  to migrate *to*; the role/playbook has to be written.
- Converge = restart = dead buttons on live messages plus a corpus refresh.
  Cutover can double-run the gateway; two gateways on one token is a visible
  fault.
- No Ansible verification surface in this repo. `just quality` proves nothing
  about a playbook.

## Grilling record

Lionel, live, three rounds — approved as the design for this ticket:
- Playbook and `ansible-vault` live **in krcg-bot**, not server-setup.
  ("I meant local as in this repo, not in server-setup.")
- Deploy artifact: **build a wheel, ship the artifact** — no PyPI dependency at
  deploy time, no git on the host.
- Trigger: **on published GitHub release**, plus a local path from the laptop.
- Secret: **`ANSIBLE_VAULT_PASSWORD` as a GitHub secret**, so CI and laptop run
  one code path.
- GitHub `DEPLOY_*` credentials stay. Consequence drawn by the session, not a
  stated decision: a CI-triggered deploy is what finally consumes them.

## Open questions

- Cutover: who accepts the restart window, and how is a double-run gateway
  prevented during the first converge?
- Do the README's generic venv+systemd self-hosting instructions survive
  unchanged? Assumed yes — `refs/shared/project.md` states self-hosting as a
  durable project fact, and this pipeline is Lionel-instance-specific.
- `just release` currently tags, pushes, builds *and* publishes to PyPI, so a
  GitHub-release trigger needs that recipe split. Not a blocker: splitting it is
  in scope here and works either way. Whether the PyPI publish step survives at
  all is the Queue topic — which is a topic, not a ticket, and so cannot block
  this per Working doctrine.

## Tasks

- Write the playbook: venv, wheel install, systemd unit from template,
  `DISCORD_TOKEN` from vault, `Restart=always`.
- Add the vault, and a `just deploy` recipe for the laptop path.
- Add the release-triggered workflow: build wheel, run playbook with
  `ANSIBLE_VAULT_PASSWORD`, `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_HOST_KEY`.
- Verify: second converge is idempotent, and a live `/card` answers after it.
