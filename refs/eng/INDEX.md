# refs/eng

Scope: architecture, Discord/hikari integration, upstream `krcg` coupling, packaging, release, hosting, quality gates.

## Stack
- Python ≥3.13, `uv` + `uv_build` backend, src layout. Deps: `aiohttp`, `hikari>=2.5,<3`, `krcg>=5.9,<6`, `unidecode`. Dev: `ipython`, `mypy`, `pytest`, `ruff`; `ansible` sits in its own `deploy` group so CI and contributors never install it.
- Both ceilings are deliberate. `krcg`: v5 was a rewrite, cadence is hot (5.0→5.9 in 22 days), and it ships `py.typed` — a minor bump can break field access and the mypy run at once. `hikari`: `GatewayBot()` parses the token in `__init__` at import time, so a major bump can make the module unimportable. Bumping either is a code change, not a lockfile refresh.
- The bot is one module: `src/krcg_bot/__init__.py` plus a three-line `__main__.py`. Keep it that way until a second surface justifies splitting.
- `hikari.GatewayBot` — a gateway (websocket) bot, not an HTTP interactions endpoint. Single process, in-memory state, no database. The gateway is chosen for testability, not inertia: an interactions endpoint needs a public HTTPS URL Discord can reach, while the gateway dials out — so the dev token runs the real bot from a laptop against a test guild. Testability is the argument, and a tunnel may answer it — unverified. Switching to a hook-based bot is an open topic (PLAN.md Queue), not a settled prohibition.
- Tooling: ruff (line-length 100, target py313), mypy on `src/krcg_bot` with untyped defs disallowed, pre-commit (ruff + whitespace/yaml hooks).
- README badges: a hardcoded badge restating a `pyproject.toml` fact drifts with nothing to catch it — the `python-3.8` and `code style-black` pair sat wrong for years (Lionel, T-005). The Python floor is the accepted exception, kept because a contributor needs it; do not add others. The Test badge is fine — it reads from Actions.

## Runtime shape
- Startup: `main()` runs `load_cards()` — `krcg.load_online()` over an `aiohttp` session — into the module-global `CARDS`, then the gateway connects. A restart is the only refresh path, which is why the bot calls `load_online` and never krcg's plain `load()`: that one reads a version-keyed `/tmp` pickle first and would serve a stale corpus forever on an unattended host.
- `load_online` swallows every failure and falls back to `load()` — the `/tmp` pickle, then krcg's packaged VEKN CSVs — and never announces it. It also *writes* that pickle (~14 MB) on each success, so a KRCG static-server outage degrades to the last good corpus rather than crashing. Two consequences: the pickle is keyed by krcg version, so a krcg bump silently empties the fallback; and the degraded corpus is indistinguishable from a fresh one in the logs. The bot package still ships no card data of its own.
- Card data shapes are krcg 5: `CardDict` keyed by id and by name, `CryptCard`/`LibraryCard` (isinstance-narrowed for mypy), typed `Ruling` objects, `variants` a list. Card text marks cards `<Name>` and italics `/like this/`; ruling text marks cards `{Name}` and carries typed `references`/`symbols`. Both name forms render italic.
- Two upstream couplings the `<6` ceiling guards, both deliberate: `import krcg.models` for `Variant.Type.BASE` (`Variant` is not in krcg's `__all__`), and `CARDS.search_index.name.search_flat(name, 25)` in `_autocomplete_cache` — `CardDict.complete()` hard-caps at 10 candidates, well under Discord's 25. Fixing the cap upstream (an `n` argument on `complete()`) would retire the second one.
- Commands are registered in `on_ready` by diffing names against the application's registered commands. Dispatch is table-driven; a new surface means touching those tables.
- Guild emojis are cached per guild in `EMOJIS` on `GuildAvailableEvent`; discipline/icon names come from `CARDS.search_dimensions["discipline"]` plus `EMOJI_NAME_MAP`.
- **The navigation stack lives in `custom_id`, and nowhere else** (T-010). A switch button is `SWITCH_PREFIX` — `switch-1`, whose trailing char versions the encoding (T-011) — then the trail as fixed-width 6-digit card ids, the target last: `_switch_id` builds it, `_parse_stack` reverses it, and `switch_card` unpacks `*stack, new_id` with no branch. No separator is needed because **every id in the corpus is exactly 6 digits**, and a 7-digit id would desync every frame after it. Two guards, deliberately unequal: `load_cards` raises at startup on any id outside the width, and `test_card_ids_are_fixed_width` catches it in CI — the test alone fires only on a push, so a quiet month lets a live bot emit bad frames first (T-011). `MAX_FRAMES` = 15, derived from the 100-char ceiling against the 8-char prefix; past it `_switch_id` drops the **oldest** frames, so a deep trail shortens from its far end and never 400s.
- Consequences of the encoding, all load-bearing: a button **survives a restart**, because it carries its own answer; a variant button inherits the trail rather than extending it (a variant is another version of the card on screen, not a step down from it — this is the T-009 defect); a ruling link appends the card on screen before its target; `< Back` is `_switch_id(stack[:-1], stack[-1])`, i.e. the trail itself. `_build_components` renders one frame short of `MAX_FRAMES`, because at the ceiling `< Back` and a ruling link truncate to the same frames on a ping-pong trail (58 mutually-citing pairs in the corpus) and Discord 400s a duplicate `custom_id`. `< Back` and the parent's own ruling-link button are both offered and are not redundant: one walks up, the other descends.
- A live button can outlive two things it depends on. The **corpus**: `_card()` is the single lookup for both handlers and raises `CommandFailed`, never `KeyError`. The **encoding**: a deploy leaves the previous release's buttons clickable for as long as their tokens last, so `_parse_stack` validates width and digits rather than letting `int()` raise — the old `switch-0-<id>` form raised `ValueError`, and `switch-<a>-<b>` parsed to silent garbage. Both funnel to a readable message; a bare `CARDS[id]` or a bare `int()` shows "Command error" instead, and a release is exactly when that is reachable. The 6-char `switch` dispatch key is deliberately *not* the version marker — every format shares it so an old button still reaches `switch_card` and gets a `CommandFailed` rather than "Command error", which is why parsing must be defensive; the version char inside `SWITCH_PREFIX` is what tells formats apart, checked ahead of width and digits (T-011), since those two agree across formats that mean different cards.
- Buttons expire on **idleness, not age** — literally, since T-010. Each navigation pushes `EXPIRY` back (`_idle_until()`) and `_expire_components` re-sleeps until it passes. Two clocks, and **only idleness may strip**: the token clamp is the watcher's own (`TOKEN_LIFETIME` from the moment *it* starts, never `message.created_at` — a watcher re-armed on an hours-old message holds a brand-new token, and the message anchor would make it strip on the spot). When the token is what ends the wait, the watcher releases its claim and strips nothing: the reader is still navigating, the buttons still answer on their own, and their next click re-arms a watcher on a fresh token. Before T-010 this had to be a strip — `HISTORY` was about to be dropped, so live buttons had to die with it. The encoding removed that reason; stripping there only breaks a reader who is present.
- Every `/card` answer parks a watcher, **public or ephemeral** — `card()` calls `_expire_components` before it knows which. `make_public` is the one answer that does not, stripping its own message inline instead.
- **An `EXPIRY` entry exists if and only if a watcher is parked on that message.** Claimed when the watcher starts, not after the first navigation, and released on every exit by the watcher and by nobody else — `make_public` deliberately does not pop it, since its own delete makes the watcher 404 and release the claim itself. Two paths race to claim: a caller holding the message passes it and claims before the first await, while `card()` must `fetch_initial_response` to learn the id at all, and a click landing inside that round-trip arms a watcher of its own. First one in owns the message; the loser returns without touching the winner's entry.
- The watcher re-checks the deadline **after** stripping, and releases on the dead-token exit so the next click re-arms on a younger token. Both are the same hazard: a click Discord accepted before the PATCH landed re-renders the buttons, and returning there would leave a live message with buttons, no entry and no watcher.
- hikari maps HTTP errors on **status alone** (`internal/net.py`), never on the JSON code: 401 → `UnauthorizedError`, 404 → `NotFoundError`, both under `ClientHTTPResponseError`. What Discord returns for an expired interaction token is *unverified* (re-checked against the docs source 2026-07-29, not merely a failed fetch): `50027 Invalid webhook token provided` is in the documented error-code table, but nothing pairs it with interaction tokens and no HTTP status is attached to it. Catch the superclass; a narrower catch bets on an unverified fact.
- `_build_components` enforces Discord's ceilings itself (5 buttons/row, 5 rows, 80-char labels) — hikari 2.5.0 validates only type homogeneity, so an over-full row reaches Discord and 400s the interaction. Drop order is a correctness decision (Lionel, T-008): `Make public` and `< Back` go in first and are never dropped, because `< Back` is the reader's only way back up the trail; variants spill to further rows; ruling links are the first sacrificed, since every one of them is reachable again through autocomplete. Every drop is logged — a button vanishing silently was the actual defect. Label truncation is display-only: it must never touch `custom_id`, which the dispatch tables and the trail both read.
- A restart abandons the per-answer expiry tasks, but the buttons still **answer** — they carry their own trail — and on an ephemeral a click that finds no entry starts a fresh watcher, so the strip is self-healing. Three residues are accepted (T-010), all the same kind — litter left for a reader who has gone, never a broken one who is present. An ephemeral nobody clicks again keeps its buttons. So does one navigated past the token clamp and then abandoned. So does every **public** message: a click on one answers with a new ephemeral rather than re-arming the public message, so nothing re-arms it whatever created it. A shutdown hook was considered and rejected: `StoppingEvent` cannot fire on SIGKILL, OOM or a host reboot, and stripping working buttons on the daily `RuntimeMaxSec` stop would destroy what the encoding buys.
- Invariants an editor must not break — Discord's hard limits, dispatch tables, the component-expiry task, the error funnel: `.claude/rules/bot-code.md`, which loads automatically when the bot code is touched.

## Workflow
- `just quality` — ruff format check, ruff check, mypy. `just test` — quality then pytest. `just serve` — run locally from `.env`.
- Tests: `tests/conftest.py` sets a dummy `DISCORD_TOKEN` before importing `krcg_bot` (hikari parses the token at import, so the module is otherwise unimportable) and exposes the corpus as the session-scoped `cards` fixture. While it loads, every krcg binding that yields local data is patched to raise: `load_online` swallows failures and falls back to a `/tmp` pickle or the packaged CSVs, which pass the whole suite and even carry the same card count. Nothing on the result tells them apart, so the fallback is made loud instead — on the live path none of those bindings is called. Without it CI is green on offline data, and CI is the one place with no pickle.
- `tests/test_bot.py` asserts shape and Discord limits, never card text, and picks its cards by shape via `find()`, never by name: upstream renames cards more often than it changes what a card is. Three tests sweep the whole corpus (embed limits, component limits, autocomplete reachability); the rest are single-card.
- Mutation-checked, and kept that way: disabling `_replace_disciplines`, the `<Name>`/`/italics/` markup, the ruling-link dedupe, the autocomplete cap or its `value`, the crypt Group, the library clan requirement, the codex `card=` param, the colour map, the Dark Pack footer, the image, or swapping the live load for a local one each reds it.
- What the suite cannot catch: it never reaches the Discord interface. `FakeInteraction` stands in for `AutocompleteInteraction` only — pinned to hikari's signature by a test, since a fake that drifts keeps the suite green while autocomplete breaks. The `card`/`switch_card`/`make_public` handlers have no coverage. The trail encoding is pure and is covered (`_switch_id`/`_parse_stack` round-trip and rejection, back, variant inheritance, ruling descent, truncation, ping-pong duplicates, retired ids). The **expiry loop is covered by neither the suite nor by hand**: its branches — the token clamp releasing, the re-check after a strip, the dead-token release, the claim race — need a 14.5-minute wait and a race to reach, so no repeatable manual check exists. It was verified by driving `_expire_components` under a virtual clock with a stand-in interaction, outside the suite because T-010 ruled that stand-in out of it. A change to that loop that is argued rather than simulated is unverified, whatever the suite says. The ≤5-rows, ≤5-buttons and ≤80-char-label assertions are inert: the corpus peaks at 4 rows, 2 variants and 35-char labels. The 100-char `custom_id` assertion is **not** inert — the corpus sweep runs at full trail depth and lands nearly tight against the ceiling. `load_cards`'s id-width guard (T-011) ships uncovered for the same reason the component caps did: only a synthetic card can reach it, and synthetic cards are ruled out below.
- Tests run against the **live corpus**, always. A committed card fixture was proposed and rejected (Lionel, T-003): tests assert against the data the bot actually serves. Consequence to accept, not fix: the suite needs the network, and a KRCG static-server outage reds unrelated PRs. Extended to **synthetic cards** (Lionel, T-008): a card is not constructed in-test to reach a branch the corpus cannot produce either. Consequence accepted, not a gap to close later — the component caps ship with no test exercising them, as the limit assertions already were.
- Manual verification of Discord-facing changes — krcg dev token, `.env`, test guild: `.claude/rules/bot-code.md` §Verification, which is its home and loads when the code is touched.
- Discord docs live at `docs.discord.com/developers/*`; `discord.com/developers/docs/*` 301s **cross-host** to it. Three ways a lookup lies (T-012): the redirect, pages past 2500 lines that truncate, and a summarizing fetch that drops individual sentences from a page which arrived whole — indistinguishable from success. The `.mdx` in `discord/discord-api-docs` is the page's own source, and greppable.
- CI: `.github/workflows/test.yml` on PRs and pushes to master — uv, py3.13, then ruff/mypy/pytest called directly. Never through `just`: it is neither a declared dependency nor on the runner, and that is what reds every run. Green on `origin/master`; the old `static.yml` ("Validation") is gone. Actions are pinned to refs that actually resolve — `astral-sh/setup-uv` publishes floating majors `v1`–`v7` only (checked 2026-07-29, `git/refs/tags`), hence the exact `v9.0.0`; reading its latest *release* and assuming a matching major ref is what failed the first run.
- Release (Lionel only): `just release` = clean, master + clean-tree check, test, `uv version --bump minor`, commit `Release X.Y`, tag, push, then `gh release create` with the wheel — that last step is what fires the deploy. `CHANGELOG.md` is hand-written, newest first. No PyPI publish (T-004); `just release` still pushes master, which is inherent — a GitHub release needs the tag pushed.
- The `krcg-bot` PyPI project **is archived** (Lionel, T-004; `project-status: archived` on the simple API, installs still resolve). **Never yank or delete it.** A freed name is a credential-harvest squat: the package takes a `DISCORD_TOKEN`, and whoever would install a squatted `krcg-bot` is exactly the self-hoster this project stopped serving. Holding the name is the standing part, whatever else changes.
- **No release until CI is green on the remote** (Lionel, T-003). Gate, not preference, and it stands for every release. Both halves are met as of v4.6: the suite is real, and `test.yml` is green on `origin/master`.
- Hosting: one instance, Lionel's, deployed by `ansible/`. Self-hosting was dropped (T-004) — no PyPI package to install, no documented venv/systemd path, and the README no longer carries one. A change to how the bot runs has exactly one consumer now.
- Deploy automation lives in this repo, not in server-setup (Lionel, T-001): server-setup ships only `nginx_site` and `postgres_db`, and a gateway bot has no listener and no database. `ansible/` ships the wheel to the host — no PyPI at deploy time, no git on the host — and `ansible/README.md` is its home: prerequisites, the vault, both trigger paths.
- The host python is not used: gravelines is Debian 12 with Python 3.11 and the wheel needs ≥3.13, so the playbook has `uv` fetch the interpreter (Lionel, T-001: "deploys simply deploy uv and use it to get the python they want"). It installs `uv` only when absent — other services on the host share it.
- The corpus cache is a UID trap. `krcg` writes `krcg_cards_<version>.pkl` into `TMPDIR`, and `load_online` *swallows* the `PermissionError` when that file belongs to another user — then falls back to reading it. Changing the runtime user without redirecting `TMPDIR` therefore pins the bot to a stale corpus forever, silently, with the unit `active`. The unit sets `TMPDIR` to a service-owned directory.
- The corpus refresh is a **scheduled restart**: the unit carries `RuntimeMaxSec=1d`, so systemd stops the bot daily and `Restart=always` brings it back on fresh data. Inherited from the legacy `myserver` deploy (`pw_daily_restart`), retired once `ansible/` converged, which also set `PYTHONOPTIMIZE=1` — kept, so `__debug__` is off and logging stays at INFO instead of DEBUG-logging every query to the journal. Dropping either is a silent regression: stale cards, or a noisy journal.
- A converge restarts only when the artifact, the token or the unit changed — a restart drops the buttons on live messages and re-fetches the corpus. Installs force `--reinstall`: uv and pip both skip a same-version wheel and still exit 0, which would report a successful deploy of code that never landed. It then checks the unit is the *same run* 20s later, since `Restart=always` makes a crash-looping bot look `active`.
- Two secrets are shared through the repo, **age-encrypted** to the public keys in `ansible/secrets/age-recipients.txt` (Lionel — the pattern is copied from `rulings-website`): the ansible-vault password, and `dev-env.age`, the development `.env` that `just serve` needs. One recipients list serves both, deliberately — two lists would drift, and the directory is `ansible/secrets/` only because that list already lived there. `ansible.cfg` points `vault_password_file` at the git-ignored `ansible/.vault_pass`; a developer age-decrypts into it, CI writes the same file from the `ANSIBLE_VAULT_PASSWORD` secret, and no path passes `--vault-password-file`. That file must exist before `--syntax-check`, not just before the converge — ansible resolves vault secrets at parse time. Removing a recipient only stops future decrypts; revoking for cause means rotating the vault password itself.
- CI credentials are split by kind, and mixing them up fails silently: `DEPLOY_SSH_KEY` and `ANSIBLE_VAULT_PASSWORD` are **secrets**, `DEPLOY_HOST` and `DEPLOY_HOST_KEY` are **variables** (`vars.`, not `secrets.` — and not masked in logs). server-setup's `just sync`/`sync-key` is what sets them.
- `gh release create` **with the wheel attached** is what fires `deploy.yml`. A tag push alone creates no release and so does not deploy.
- One artifact per release, and **nothing else is deployable** (Lionel, T-001): the release carries the wheel, and both CI and `just deploy` converge *that file*. No path ships a working-tree build, so what runs in production always answers to a tag, and rollback is `just deploy <tag>` or `workflow_dispatch` with it. Builds are byte-reproducible (`uv build` twice over one source gives one sha256), so rebuilding would have been *correct* — it was rejected anyway: two artifacts claiming to be one release, and no way to redeploy an old one. Consequence to accept: trying a change on the host means cutting a release.

## Grilling angles
- Which Discord API limit does this hit first — rows, field length, the 3s acknowledge budget?
- What does it cost at startup and in memory, given the whole corpus is resident?
- Does it survive a restart? A button must carry everything needed to answer it — what new state does this add, and who rebuilds it?
- What does it assume about upstream `krcg` (data shape, rulings format, version floor) — and how does it fail when that changes?
- How is it verified? The suite asserts shape over the live corpus and never touches Discord: name the test it adds, or the manual check that covers what tests cannot.
- Does it still work with zero server configuration (no custom emojis, no permissions beyond the default)?
